# Аргументация разделения на домены и преимущества для бизнеса

## Логика разделения

### 1. Изоляция медицинских данных (MedicalRecords)
- **Почему отдельно**: регуляторные требования (врачебная тайна, 152-ФЗ, GDPR).
- **Как работает**: домен физически отделён. BI портал не имеет к нему доступа. Только AI-сервисы могут получать обезличенные данные по строгому контракту.
- **Бизнес-ценность**: снижение юридических рисков, возможность проходить аудиты.

### 2. Fintech — независимый домен
- **Почему отдельно**: банковская лицензия требует отдельной отчётности, аудита, высокой доступности.
- **Как работает**: Fintech не зависит от DWH клиник. Может масштабироваться в облаке отдельно.
- **Бизнес-ценность**: выпуск новых кредитных продуктов за 2-3 недели вместо 2-3 месяцев.

### 3. Clinics — операционный домен
- **Почему отдельно**: критичен для основной деятельности (приёмы, инвентарь). Не должен тормозиться из-за финансовых отчётов.
- **Как работает**: данные о загрузке и персонале — в своём хранилище. Агрегаты отдаёт через API.
- **Бизнес-ценность**: надёжность записи пациентов (99.9% доступности).

### 4. AI Services — домен интеллектуальной обработки
- **Почему отдельно**: требует GPU-ресурсов, больших данных, специфичных пайплайнов.
- **Как работает**: получает обезличенные данные из MedicalRecords, возвращает метрики (не сырые диагнозы).
- **Бизнес-ценность**: ускорение внедрения новых моделей диагностики без изменения DWH.

### 5. Pharma, Electronics — подключаемые домены
- **Почему отдельно**: новые бизнес-направления не должны зависеть от legacy DWH.
- **Как работает**: регистрируются в Data Mesh, обмениваются агрегатами через API Gateway.
- **Бизнес-ценность**: M&A (покупка фарм-компании) интегрируется за 2-4 недели, а не за полгода.

## Преимущества для бизнеса (таблица)

| Бизнес-задача | Без доменов (текущая архитектура) | С доменами (целевая) | Выигрыш |
|---------------|-----------------------------------|----------------------|---------|
| Вывод нового кредитного продукта | 2-3 месяца (согласование с DWH) | 2-3 недели (только Fintech) | **в 4 раза быстрее** |
| Интеграция фарма-партнёра | 4-6 месяцев (перестройка ESB + DWH) | 2-4 недели (новый домен + API) | **в 6 раз быстрее** |
| Обучение новой ИИ-модели на снимках | Риск утечки медданных, долгий ETL | Безопасно, через обезличенный API | **снижение риска + скорость** |
| Отказ кредитного сервиса | Ложит DWH → клиники не работают | Только Fintech недоступен | **устойчивость + изоляция** |
| Создание управленческого отчёта | Часы (JOIN по 100+ ТБ) | Минуты (агрегаты из доменов) | **производительность ×10** |

## Как это поддерживает ключевые сценарии из кейса

1. **Портал самообслуживания**  
   BI-портал работает только с агрегатами доменов (Fintech, Clinics, AI). MedicalRecords исключён. Это соответствует требованию "медицинские карты не будут включаться в витрину".

2. **Независимое развитие финтех и ИИ**  
   Fintech и AIServices не знают о внутреннем устройстве друг друга. Могут использовать разные технологии (Golang/Java и Python), разные базы данных.

3. **Масштабирование для новых бизнесов**  
   Pharma и Electronics — отдельные домены. Подключаются через API Gateway без изменения существующих систем. DWH остаётся только для исторических данных.

4. **Отказ от легаси-систем**  
   Старый DWH на SQL Server 2008 становится архивом (read-only). ESB заменяется на API Gateway + асинхронную шину (Kafka/Pulsar). PowerBuilder уходит вместе с клиентским интерфейсом оператора (заменяется на веб-интерфейс).

## Риски и их митигация

| Риск | Митигация |
|------|-----------|
| Сложность миграции с DWH на домены | Инкрементальный подход: сначала Fintech, потом Clinics, потом AI |
| Дополнительная задержка при междоменных запросах | Кэширование агрегатов, асинхронные события вместо синхронных вызовов |
| Нужна культура Data Mesh (ownership данных) | Обучение команд, назначение Data Owner'ов в каждом домене |
