# Анализ проблемных мест

| ID | Проблема | Где на схеме | Проявление | Бизнес-сценарии под угрозой |
|----|----------|--------------|------------|------------------------------|
| **PR1** | **Монолитность DWH** | DWH (центр схемы) | Все данные (медицина + финансы + ИИ) в одной БД. Изменение структуры под финтех ломает отчёты клиник. | • Вывод нового кредитного продукта — месяцы<br>• Масштабирование на фарма-партнёров |
| **PR2** | **Медкарты могут попасть в BI** | DWH → BI (по вашей схеме) | BI-система имеет прямой доступ к DWH, где лежат сырые медицинские данные. | • Нарушение 152-ФЗ (врачебная тайна)<br>• Риск отзыва лицензии у банка |
| **PR3** | **ESB — единая точка отказа и тормоз** | ESB (центр) | Все потоки через Apache Camel. При сбое ESB останавливаются клиники, финтех и ИИ. | • Операторы не видят расписание приёмов<br>• Остановка выдачи кредитов |
| **PR4** | **Нет самообслуживания аналитиков** | BI система (справа) | Каждый отчёт требует кастомизации в BI поверх DWH. | • Задержка управленческих решений (часы → дни)<br>• Нельзя быстро проверить гипотезу |
| **PR5** | **Бизнес-логика размазана** | DWH + PowerBuilder + ESB | Логика расчётов дублируется. Чтобы изменить правило кредитного скоринга, нужно править 3 системы. | • Time-to-market новых фич — недели/месяцы<br>• Ошибки при согласовании логики |
| **PR6** | **Масштабирование ресурсов невозможно** | DWH на SQL Server 2008 | При росте данных (сотни ТБ) отчёты тормозят, нельзя добавить горизонтальные ноды. | • Рост числа клиентов → падение производительности<br>• Невозможно подключить нового производителя электроники |
| **PR7** | **Нет изоляции доменов** | Вся схема | Сбой в отчёте по кредитам нагружает DWH → клиники теряют доступ к истории болезней. | • Критичные медицинские сервисы зависят от финансовой аналитики |
